# Maintainer Guide

Maintainer-facing documentation for the hep-metadex repository itself: where
its workflow setup came from, how it intentionally diverges from its template,
and how to update from upstream without losing those divergences.

Adopters do not need this document to use the store or install the
[workflow scaffolding](../glossary/technical.md) — see the
[README quick start](../README.md#quick-start) and [setup.md](setup.md).
This guide exists so the template relationship stays explicit and template
syncs stay deliberate.

## Template Provenance

This project's OpenSpec/OpenCode setup was installed on 2026-11-03 from
[intent-driven-template](https://github.com/intent-driven-dev/intent-driven-template)
at commit `b5bda460a2180a55fc508fdedc4ef058d95355db` (2026-10-15), following
its
[install guide](https://raw.githubusercontent.com/intent-driven-dev/intent-driven-template/refs/heads/main/INSTALL_TEMPLATE.md).
The bundled schema under `openspec/schemas/intent-driven/` is a local copy of
the [intent-driven schema](https://github.com/intent-driven-dev/openspec-schemas/tree/main/openspec/schemas/intent-driven)
from the openspec-schemas repository. The shared lifecycle commands and
skills under `.opencode/` are OpenSpec CLI 1.16.0 versions, newer than the
template's copies (generated by 1.14.0).

hep-metadex doubles as the **workflow scaffolding template source**: adopting
experiments install these files from versioned
[kit releases](../glossary/technical.md) (see [setup.md](setup.md)), which
makes the divergence manifest below the replication discipline for the whole
family of repositories.

## Intentional Divergences

The files below intentionally differ from upstream. Treat this table as the
manifest when syncing with the template:

| Area | Divergence | Reason |
|------|------------|--------|
| `.opencode/commands/`, `.opencode/skills/` | Shared commands and skills are CLI 1.16.0 versions (template ships 1.14.0); `opsx-update` and `openspec-update-change` exist only locally | Avoided a downgrade; these files are CLI-owned, not template-owned |
| `opencode.json` | Renamed to `opencode.json.example` | Per-project OpenCode config is opt-in; global config is preferred |
| `openspec/config.yaml` | Active `context` block (tech stack, conventional commits, HEP domain, subagent routing) and all stage rules enabled | Project-specific configuration; designated customization point |
| `openspec/schemas/intent-driven/templates/spec.md` | "business rule" placeholders changed to "domain rule" | This is a high-energy physics domain, not a business domain; the local schema copy is the designated customization point |
| `.agents/skills/glossary/` | `glossary/business.md` convention renamed to `glossary/domain.md` (SKILL.md, README.md) | HEP domain terms should not be filed under a "business" label; **this is a fork of a vendored skill** |
| `.agents/skills/openspec-git-discipline/` | The "Before propose" and "After propose" gates amended to require the `<issue-number>-<change-slug>` issue branch cut from `main` before a change's first commit | Standing policy that change work reaches `main` only by pull-request merge — **this is a fork of a vendored skill** |
| `.gitignore` | Minimal local file (template ships a broader one) | Only `openspec/.cache/` and `.venv/` are needed so far |
| `AGENTS.md` | Added a pointer to `docs/intent-prompt-guidelines.md` for intent-prompt authoring | Project-specific contributor guidance; re-apply the pointer after a template sync |
| `LICENSE` | Full Apache-2.0 license at the repository root instead of the template's MIT `LICENSE.md` | Deliberate divergence: a cross-institution standards artifact needs the explicit patent grant and contribution terms — see [ADR-0004](../adr/0004-apache-2-license-diverging-from-template-mit.md) |
| `.github/workflows/validate.yml` | Spec-validation CI added (the template ships no CI); distributed with the [workflow scaffolding](../glossary/technical.md) — GitHub-hosted adopters copy this file at bootstrap ([ADR-0005](../adr/0005-distribute-spec-validation-ci-as-host-conditional-scaffolding.md)) | Gates `openspec validate --all` on `valid: true`, non-strict, per [ADR-0003](../adr/0003-fenced-gherkin-single-source-validation-gate.md); the OpenSpec CLI version is pinned in the workflow |
| `.github/ISSUE_TEMPLATE/` | Issue form added (the template ships none): the intent-material change form (`change.yml`) plus the config disabling blank issues (`config.yml`); distributed with the [workflow scaffolding](../glossary/technical.md) — GitHub-hosted adopters copy both at bootstrap ([ADR-0008](../adr/0008-route-workflow-conventions-to-kit-layers.md) routes host-conditional automation to `.github/`) | Standardizes issue authoring on the intent-material template ([#23](https://github.com/DUNE/hep-metadex/issues/23)); the form is the GitHub implementation of a host-neutral convention — repositories on other hosts replicate it natively |
| `.metadex-kit`, `KIT-MANIFEST.yaml` | New kit identity files (the template ships none): the version file — source-side release trigger, provenance stamp when installed — and the kit's per-path bill of materials; distributed with the workflow scaffolding — adopters install both from the [kit release](../glossary/technical.md) bundle ([ADR-0009](../adr/0009-distribute-workflow-scaffolding-as-versioned-kit-releases.md)) | Kit release channel identity; the future update path ([#39](https://github.com/DUNE/hep-metadex/issues/39)) reconciles by the manifest's ownership classes |
| `.github/workflows/release.yml` | Kit release workflow (the template ships none): repo-local maintainer automation, never part of the workflow scaffolding — the `docs.yml` pattern ([ADR-0009](../adr/0009-distribute-workflow-scaffolding-as-versioned-kit-releases.md)) | Tags `vX.Y.Z` on a kit version bump and publishes the bundle plus `SHA256SUMS` with the changelog section as the release body; creates tags and releases only, never commits |
| `CHANGELOG.md` | Kit changelog (the template ships none): repository documentation, never shipped in the bundle — the docs link to it ([ADR-0009](../adr/0009-distribute-workflow-scaffolding-as-versioned-kit-releases.md)) | The single source of GitHub release bodies; kit-altering changes land their entry with the version bump in the same change |
| Not installed | `package.json`, `package-lock.json`, `skills-lock.json` | Outside the install guide's file list; do not add during a sync without a deliberate decision |
| `pyproject.toml`, `uv.lock`, `.python-version` | Repo-local [maintainer toolchain](../glossary/technical.md) files the template never ships ([ADR-0006](../adr/0006-python-uv-as-repo-local-maintainer-toolchain.md)) | Outside the install guide's file list; do not add during a sync without a deliberate decision |
| `zensical.toml`, `tools/`, `.github/workflows/docs.yml` | Repo-local [documentation site](../glossary/technical.md) tooling the template never ships ([ADR-0007](../adr/0007-publish-zensical-docs-site-on-github-pages.md)) | Outside the install guide's file list; do not add during a sync without a deliberate decision |

## Drift Impact

- **Designated customization points** (`openspec/config.yaml`, the local
  `openspec/schemas/intent-driven/` copy): upstream changes must be
  reconciled manually. A naive copy loses the project-specific values listed
  above.
- **Vendored skill fork** (`.agents/skills/glossary/`): a template sync that
  overwrites this directory silently reverts `glossary/domain.md` back to
  `glossary/business.md`. Re-apply the rename after updating, or merge
  upstream changes by hand.
- **Vendored skill fork** (`.agents/skills/openspec-git-discipline/`): a
  template sync that overwrites this directory silently reverts the two
  amended gates ("Before propose" cuts the issue branch; "After propose"
  opens the planning PR from it). Hand-merge upstream changes into the
  skill and re-apply both gates after any sync.
- **CLI-generated files**: never copy the template's versions of the shared
  commands and skills over the local ones — the template currently ships
  older (1.14.0) versions than the installed CLI (1.16.0) produced. Update
  these via the OpenSpec CLI instead.
- **`README.md`**: project-owned documentation, not template-managed; a sync
  should not overwrite it.
- **Experiment repositories**: the same manifest governs what adopting
  repositories install from here. When a divergence above changes a file that
  [setup.md](setup.md) tells adopters to copy, the change note should say so,
  and adopters re-install the kit from a newer
  [kit release](../glossary/technical.md) to pick it up — the `.metadex-kit`
  stamp records which release they carry ([#39](https://github.com/DUNE/hep-metadex/issues/39)
  will mechanize the sync).

## Updating From Upstream

1. **Record the baseline.** Before syncing, note the current upstream commit;
   after syncing, update the commit hash at the top of
   [Template Provenance](#template-provenance). Commit
   all local work first and sync on a branch.
2. **Never bulk-copy.** Clone the template outside the repository, diff it
   against the project, and copy only files that changed upstream and are not
   listed in the divergence manifest.
3. **Update CLI-owned files via the CLI.** Refresh the shared commands and
   skills under `.opencode/` with the OpenSpec CLI (`openspec --version` to
   check), not from the template.
4. **Re-apply the manifest.** After copying any template file, re-apply every
   affected divergence from the table above (config values, spec template
   wording, glossary rename).
5. **Validate before merging.** Run `openspec schema validate intent-driven`,
   review the full `git diff`, and merge only when the result matches the
   manifest.

## Kit Releases

The **workflow scaffolding** ships as semantically versioned, checksum-verified
[kit releases](../glossary/technical.md) ([ADR-0009](../adr/0009-distribute-workflow-scaffolding-as-versioned-kit-releases.md)).
This is the release discipline:

- **Bump with the change.** A change that alters kit files bumps the version
  in `.metadex-kit` and lands the matching `CHANGELOG.md` entry in the same
  change — the same discipline as the CLI pin (see
  [usage.md](usage.md#cli-version-pinning-and-upgrades)). When the change
  merges to `main`, the release workflow cuts the release automatically.
- **The version speaks about the kit only.** MAJOR — breaking changes to
  installed state (schema format changes, command renames or removals,
  coordinated CLI upgrades); MINOR — new kit components; PATCH — fixes and
  wording. Changes confined to specs, changes, non-kit docs, or repo-local
  tooling never drive a release.
- **Changelog conventions.** `CHANGELOG.md` follows
  [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): version headings
  with dates, categorized entries, each referencing its change issue in the
  `(#N)` style. A section's date is written when the change is prepared; the
  GitHub release's own timestamp is authoritative. There is no Unreleased
  section — a kit-altering change always releases on merge.
- **Release mechanics.** `.github/workflows/release.yml` (repo-local, never
  kit) detects the bump by diffing `.metadex-kit` against the latest `v*`
  tag — the file's introduction counts as the first bump — then refuses to
  release unless the changelog section exists, `.metadex-kit`'s `cli:` pin
  matches `validate.yml`, and the version's tag does not already exist. It
  publishes the bundle (exactly the copy-list plus `.metadex-kit` and
  `KIT-MANIFEST.yaml`), `SHA256SUMS`, and the changelog-sourced release body
  with the required CLI version declared. It creates tags and releases only —
  never commits on `main` — and uses no release-please-style PR generation.
- **When a run misfires**, re-run via `workflow_dispatch` (the workflow's
  manual trigger) after fixing the cause; the gates re-check everything
  before publishing.

## Repository Configuration

- `openspec/config.yaml` selects the intent-driven schema and per-artifact
  rules (see [usage.md](usage.md) for the stage table). Its `context` block
  injects project background (domain, tech stack, subagent routing) into
  every artifact workflow.
- `AGENTS.md` enables OpenSpec git discipline: proposals land on `main`
  before apply, and implementation merges before archive.
- `.opencode/agent/` provides `senior-dev`, `senior-qa`, and adversarial
  author/reviewer subagents.
- `.agents/skills/` provides collaboration skills: `grill-me`, `c4-diagrams`,
  `architectural-decision-records`, `test-driven-development`,
  `gherkin-authoring`, `glossary`, `spec-as-source`, and more.
- The kit's layers divide responsibility by the routing rule in
  [ADR-0008](../adr/0008-route-workflow-conventions-to-kit-layers.md): the
  schema for artifact structure inside changes, `openspec/config.yaml` rules
  for per-stage discipline, skills for agent-triggered discipline, commands
  for procedure automation, the intent-prompt guidelines doc for authoring
  guidance, and `.github/` for host-conditional automation.
- `opencode.json.example` is an optional stub for per-project OpenCode
  configuration. OpenCode reads your global config
  (`~/.config/opencode/opencode.json`), which applies to every project, so
  this repo ships no active `opencode.json`. Copy the stub to
  `opencode.json` only if you need repo-specific settings (e.g., the optional
  Superpowers plugin). The stub contains only the `$schema` reference for
  editor validation and configures nothing.
