## Why

The agent-assisted bootstrap documented in `docs/setup.md` is proven — the manual procedure was dogfooded on dune-metadex — but it is friction-heavy copy-paste: every adopter initializing an **Experiment repository** hands a long prompt to an agent and trusts it to follow every step. The bootstrap change (#7) deferred encoding it as a command so it would "encode proven steps rather than guesses"; with the versioned **Kit release** channel (#34) and its enforced release discipline (#35) now in place, the `/hep-metadex-bootstrap` command is born version-aware instead of retrofitted, dropping adoption friction from "paste this prompt" to "run this command".

## What Changes

- **The command — the first kit-owned command:** `/hep-metadex-bootstrap` ships as an OpenCode command file at `.opencode/commands/hep-metadex-bootstrap.md`, in the **Workflow scaffolding** so it flows to experiment repositories by template install. It is zero-runtime agent instructions, not a script, following the command shape of the CLI-delivered files already in that directory. The `hep-metadex` prefix keeps kit commands out of the bare `metadex-*` namespace adopters may claim for their own commands while disambiguating from the CLI-owned `/opsx-*` lifecycle.
- **End-to-end bootstrap automation:** the command automates the documented prompt end to end, for greenfield and brownfield repositories alike: prerequisites check (agent harness; OpenSpec CLI version against the release's declared pin; **OpenSpec Store** registration), `openspec init`, kit install from a versioned **Kit release** with SHA256SUMS verification — latest by default, an explicit version pin accepted — kit file placement at natural paths (`AGENTS.md` merged per its merge-guidance class, never overwritten; the **Kit version file** and KIT-MANIFEST arriving via the bundle, the version file landing as the **Experiment repository**'s provenance stamp, not authored by the command), host-conditional GitHub files, `openspec/config.yaml` authoring, and `openspec doctor` iterated to green.
- **The one-liner:** a documented one-liner fetches the command file from the latest **Kit release** and hands it to the agent — resolving the bootstrap chicken-and-egg, since a fresh repository has no scaffolding and therefore no command until this fetch. This is the command-file fetch for agent-assisted bootstrap, distinct from #38's agent-free installer one-liner.
- **Release asset:** the repo-local release workflow additionally publishes the command file as a standalone, checksummed release asset — derived from the same source file that enters the bundle, one source of truth — so the one-liner has a pinnable, verified target rather than a floating main-branch URL.
- **Manifest per-file entry:** `KIT-MANIFEST.yaml` gains `.opencode/commands/hep-metadex-bootstrap.md` → kit-owned alongside the existing cli-owned `.opencode/commands/` directory entry, with most-specific-matching-path precedence: the future update path (#39) kit-refreshes this one file while CLI-generated `opsx-*` files stay cli-owned. The command file ships in the bundle through the directory entry — bundle assembly reads every `paths:` entry regardless of ownership class, which governs the refresh route, not bundle membership — so the per-file entry exists for ownership semantics, and the copy-list gains one entry. Because the `paths:` block is the single copy-list source, the release workflow, the **Kit reminder**, and the **Kit release gate** all see the entry by construction — no `kit-release-discipline` change is needed.
- **Documentation:** `docs/setup.md` presents the command as the primary agent-assisted bootstrap, with the documented prompt remaining the fallback and the specification the command automates (its steps stay as #34 landed them), and documents the one-liner; `docs/usage.md`'s ownership-class guidance gains the per-file kit-owned exception to "CLI-owned paths refresh via `openspec update`"; `docs/maintainer.md`'s divergence manifest gains a row for the first kit-owned command (a kit command inside a cli-owned directory) and its release-workflow row's description extends to the published command asset.
- **Glossary:** `glossary/technical.md` gains a `Bootstrap command` term.
- **Kit release:** the kit version bumps MINOR, 1.0.1 → 1.1.0 (new kit component), with the **Kit version file** bump and its matching `CHANGELOG.md` entry landing in this change; the merge cuts kit v1.1.0 — the first end-to-end dogfood of #35's reminder and archive gate (ADR-0010).

## Capabilities

### New Capabilities
- `bootstrap-command`: The `/hep-metadex-bootstrap` command — its delivery through the kit and its bootstrap behavior in the target repository, working for greenfield and brownfield **Experiment repositories** alike. Requirement areas, so the specs stage can make each independently testable:
  - Delivery: the command ships in the **Workflow scaffolding** and flows to experiment repositories by template install.
  - One-liner bootstrap: a documented one-liner fetches the command file from the latest **Kit release** and hands it to the agent, so an uninitialized repository can bootstrap without pre-existing scaffolding.
  - Specification fidelity: the documented prompt in `docs/setup.md` is the specification the command automates — drift between them is a defect.
  - Prerequisites: agent harness, OpenSpec CLI version against the release's declared pin, and **OpenSpec Store** registration are verified before proceeding, stopping with a clear report when any is missing.
  - Initialization: `openspec init` runs for the repository's agent tools.
  - Versioned install: the kit is installed from a versioned **Kit release** — latest by default, an explicit version pin accepted — with SHA256SUMS verification; kit files land at their natural paths, `AGENTS.md` is merged per its merge-guidance class, and the **Kit version file** arrives via the bundle as the provenance stamp, never authored by the command.
  - Host-conditional files: GitHub-hosted repositories keep the spec-validation workflow and the issue form; repositories on other hosts have the extracted `.github/` kit files removed and the equivalent `valid: true` gate and **Intent material** issue convention named for their own tooling.
  - Config authoring: `openspec/config.yaml` is authored with schema, **Store reference** block, context block, and stage rules — never a `store:` line; in brownfield repositories nothing existing is overwritten beyond the references block.
  - Doctor to green: `openspec doctor` is iterated until it reports the reference as ok.
  - Guardrails and report: no change is created and no implementation code is written in the target repository, and the run ends with a report of what was installed and the final doctor output.

### Modified Capabilities
- `kit-releases`: The "KIT-MANIFEST ownership classes" requirement gains per-file granularity — a kit-owned file inside the cli-owned `.opencode/commands/` directory, with most-specific-matching-path precedence; the "Bump-triggered release publication" requirement additionally publishes the command file as a standalone, checksummed release asset; the release-consumption documentation requirement's ownership guidance in `docs/usage.md` carries the per-file exception.
- `adopter-onboarding`: The agent-assisted bootstrap documentation presents the command as the primary path, with the documented prompt remaining the fallback and the specification the command automates, and documents the one-liner in `docs/setup.md` (the README quick start already points there). Host-conditional CI and issue-form behavior is unchanged — the command automates the same conditional steps.

## Impact

- **Repositories:** hep-metadex gains `.opencode/commands/hep-metadex-bootstrap.md`; `KIT-MANIFEST.yaml` (per-file entry), the repo-local release workflow (asset publication), `docs/setup.md`, `docs/usage.md`, `docs/maintainer.md`, `glossary/technical.md`, `CHANGELOG.md` (v1.1.0 section), and `.metadex-kit` (version bump) change. Spec deltas: new `bootstrap-command`; modified `kit-releases` and `adopter-onboarding`.
- **No breaking changes:** An additive kit component (MINOR). The documented prompt keeps working as the fallback; already-bootstrapped repositories are untouched until they choose to update (#39); nothing existing is removed or renamed.
- **Sanctioned divergence:** the documented prompt pins the OpenSpec CLI by hand (1.16.0 today, frozen as #34 landed it) while the command checks the release's declared pin; the two coincide today and diverge by design as releases move — the prompt stays the static fallback, the command is version-aware.
- **Tool dependency:** None new for adopters — the command is zero-runtime agent instructions whose externals (the OpenSpec CLI, an agent harness, and curl for the one-liner) are already prerequisites of the documented path. The release-workflow edit adds no new Actions (the runner's preinstalled `gh`, as today) and stays within the workflow-action-pinning discipline.
- **Process:** Tracks issue #9, whose **Intent material** is the authoritative request; the gate — #34 and #35 archived — is satisfied (progression #34 → #35 → this change → #39). **Issue branch** `9-add-metadex-bootstrap-command` cut from `main` before the first commit; work reaches `main` only by pull-request merge; commits carry the `(#9)` subject suffix. The archive phase runs the **Kit release gate** (`uv run tools/kit_release_gate.py 9`) and refuses until the published v1.1.0 contains this change's kit changes — the gate's first dogfood.
- **Downstream:** Adopters bootstrap with one command (or one fetched, checksummed file) instead of a pasted prompt — dune-metadex is the worked example. The per-file ownership entry establishes the most-specific-path precedence the #39 update path will rely on. A post-bootstrap repository holds the fetched command file that the kit install then re-delivers — identical in the default latest-release path, potentially divergent under a pin — an explicit input to #39.
- **Out of scope:** #39 update/sync semantics for already-bootstrapped repositories; #36 release signing; #37 spec versioning; #38's agent-free installer one-liner; store-mechanism changes; changing the documented prompt's procedure beyond its reframing as fallback and specification.
- **Deferred to design:**
  - The pin-check mechanism: where the command reads the release's declared CLI pin (release body vs the bundled `.metadex-kit`).
  - The exact version-pin argument syntax the command accepts.
  - Where the one-liner is surfaced besides `docs/setup.md` (a README quick-start pointer among the options).
  - How the release workflow derives and checksums the standalone command asset.
  - Bundle assembly with a per-file entry nested inside a directory entry (duplicate-member handling), preserving the single-source copy-list contract.
  - Behavior when the fetched command file is newer than the pinned kit it installs (warn, refuse, or fetch the matching release's file).
