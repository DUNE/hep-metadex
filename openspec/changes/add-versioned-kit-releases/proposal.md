## Why

Channel 2 (ADR-0001) distributes the kit — the installable **Workflow scaffolding** — by template install from an unpinned checkout of the **OpenSpec Store**: installs leave no provenance record in the **Experiment repository**, and the maintainer guide's update path ("adopters re-run the scaffolding install") cannot say what changed since the last install. The tension underneath is structural — the kit wants pinning (drift is ADR-0001's named bad consequence) while channel 1's registered checkout must keep floating on `main`, because spec consumption and **Write-back** assume current specs, and both channels flow from the same clone. This change gives the kit its own release identity — cut by maintainers, installed by adopters as a pinned, verified kit — while the first adopter is still cheap to stamp and the gated follow-ons (#9, #39) wait on it.

## What Changes

- **Versioned kit releases (ADR-0009):** A new ADR records the channel-2 source refinement: the kit flows from semantically versioned, checksum-verified release bundles rather than the raw store checkout; versioning is kit-only — the number describes the kit copy-list, never spec content; kit pinning and spec freshness are decoupled; and the kit version file is the release trigger.
- **Kit version file:** A version file at the repository root (suggested name `.metadex-kit`; exact name and format are a design-stage decision) carries the kit's current version. It plays two roles: source-side it triggers the release; shipped inside the bundle it is each adopter's provenance stamp, so every install lands pre-stamped.
- **Release workflow:** A repo-local GitHub Actions workflow (never kit-shipped, like docs.yml). When a version bump merges to `main`, it tags `vX.Y.Z`, assembles the kit bundle — exactly the documented copy-list plus the version file and a machine-readable KIT-MANIFEST — generates SHA256SUMS, and publishes the GitHub release with its body extracted from the changelog section for that version (the release fails if that section is missing) and the required OpenSpec CLI version declared (currently 1.16.0). It creates tags and releases only — never commits on `main` — and uses no release-please-style PR generation, which would create issue-less commits and fight the change lifecycle and git discipline.
- **KIT-MANIFEST:** A machine-readable, per-path bill of materials shipped in the bundle, carrying ownership classes: CLI-owned (`.opencode/commands/`, `.opencode/skills/` — refreshed via the OpenSpec CLI, never kit-copied over), kit-owned (`.opencode/agent/`, `.agents/skills/`, the schema copy, `docs/intent-prompt-guidelines.md`, host-conditional `.github/` files), merge-guidance (`AGENTS.md`), and never-touch (`openspec/config.yaml`).
- **Kit semver contract:** MAJOR — breaking changes to installed state (schema format changes, command renames or removals, coordinated CLI upgrades); MINOR — new kit components; PATCH — fixes and wording. The number speaks about the kit only: changes confined to specs, OpenSpec changes, non-kit docs, or repo-local tooling never drive a kit release.
- **CHANGELOG.md:** A root changelog maintained per Keep a Changelog — semver-compliant version headings with release dates, categorized entries, each entry referencing its change issue — as the single source the release workflow extracts each GitHub release body from. Any change that alters kit files bumps the kit version and adds the matching changelog entry in that same change, mirroring the CLI-pin discipline (usage.md, "CLI Version Pinning and Upgrades").
- **Documentation:** The README quick start (steps 4–5), the setup.md two-channels section, and the bootstrap prompt install the kit from the release bundle; maintainer.md gains divergence-manifest rows for the release workflow (repo-local, never kit) and the version file (new kit file), plus a release-process section; usage.md gains adopter-facing release consumption including the manual SHA256SUMS verification step (the documented check until the update command, #39, and any installer, #38, automate it). Docs pages link `../CHANGELOG.md` — usage.md's release consumption and the maintainer guide's release process are the natural anchors — and the existing out-of-tree link machinery rewrites those links to the changelog's GitHub URL, keeping it reachable from the **Documentation site**.
- **Channel 1 untouched:** Store registration, **Store reference** consumption, **Spec index** injection, and the doctor fix are unchanged; the registered checkout keeps floating on `main`, so **Common capability** specs stay fresh for consuming experiments.
- **Dogfood (v1.0.0):** This change ships the kit's first version stamp — the version file at 1.0.0 with its matching changelog entry — so the version-bump merge cuts kit v1.0.0. The release workflow's first-ever run is triggered by the very merge that introduces it, so first-release success is an explicit acceptance focus with a manual workflow re-run as the fallback; maintainers then re-run the kit install on dune-metadex from the release, giving the first adopter its provenance stamp. The dune-metadex re-install is post-merge verification, tracked as the change's final task.
- **Out of scope:** CI reminder and archive-gate enforcement (#35); the bootstrap command (#9) and the update command (#39); release signing (#36); spec versioning (#37); an installer one-liner (#38); and shipping the changelog inside the kit bundle — it is repository documentation that the documentation set links to rather than installs (command-side changelog consumption arrives with #39).

## Capabilities

### New Capabilities
- `kit-releases`: The versioned release channel for the kit, spanning distinct requirement areas the spec stage will make independently testable: the kit-only semver contract (MAJOR/MINOR/PATCH meanings; the number never describes spec content); the version file's dual role (source-side release trigger, shipped provenance stamp); the bump-triggered release workflow (tags `vX.Y.Z`; bundles exactly the copy-list plus version file and KIT-MANIFEST; publishes SHA256SUMS; extracts the release body from the changelog section and fails when it is missing; declares the required OpenSpec CLI version; creates tags and releases only, never commits on `main`); changelog discipline for kit-altering changes; and channel-1 preservation.

### Modified Capabilities
- `adopter-onboarding`: The documented install source becomes the versioned kit release bundle — pinned, checksum-verified, pre-stamped with provenance — instead of the raw hep-metadex checkout: the quick start, host-conditional CI, host-conditional issue-form, and divergence-manifest requirements re-point to the release bundle, and the divergence-manifest framing gains the kit version file (new kit file) and the release workflow (repo-local, never kit).

## Impact

- **Repositories:** hep-metadex gains ADR-0009 under `adr/`, a root kit version file, a root `CHANGELOG.md`, and a repo-local release workflow under `.github/workflows/` alongside docs.yml; documentation edits land in the README quick start, setup.md, usage.md, and maintainer.md. dune-metadex re-receives the kit from the v1.0.0 release and gains its provenance stamp.
- **No breaking changes:** The kit's installed file content is unchanged, and v1.0.0 establishes the baseline kit — the version file and KIT-MANIFEST are part of the initial kit's composition, not increments to a prior release (the MINOR class governs kit components added after 1.0.0). Channel 1 — **OpenSpec Store** registration, **Store reference** consumption, **Spec index** injection — is untouched, and existing installs keep working until they choose to adopt a release.
- **Tool dependency:** None new for adopters — the kit stays zero-runtime. The release workflow is repo-local maintainer automation, sibling to the docs workflow and the **Maintainer toolchain**, and never ships in the kit; each release declares the OpenSpec CLI version the kit requires (1.16.0 today).
- **Process:** Tracks issue #34, whose **Intent material** is the authoritative request. Work follows an **Issue branch** `34-add-versioned-kit-releases` cut from `main` before the first commit; conventional commits carry the `(#34)` subject suffix; the change reaches `main` only by pull-request merge. This change itself performs the v1.0.0 version bump and changelog entry; the release cut and the dune-metadex re-install follow the merge.
- **Downstream:** Unblocks #9 (bootstrap command) and #39 (update command); lays groundwork for #35 (CI reminder and archive-gate enforcement); establishes the base that #36 (release signing), #37 (spec versioning), and #38 (installer one-liner) will extend.
- **Deferred to design (not settled here):** the version file's exact name and format; bundle packaging details; changelog entry mechanics (heading-in-bump-change vs Unreleased accumulation, date stamping); and whether the changelog is additionally published as a **Documentation site** page or reached only via rewritten GitHub links.
